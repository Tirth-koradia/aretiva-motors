## What you must build

- MongoDB
- SQLite

### 3. Authentication

Users must be able to register and log in. After a successful login, the backend returns a token—most likely a JWT—which the frontend sends with protected requests.

A secure implementation should also ensure:

- Passwords are hashed, never stored as plain text.
- Normal registration always creates a normal user.
- A person cannot send `"role": "admin"` and make themselves an admin.
- Admin accounts are created through a seed or bootstrap process.
- JWT secrets are stored in environment variables.
- Invalid or expired tokens are rejected.

### 4. React frontend

- React
- Tailwind
- HTML5
- CSS3

It must have:

- Registration page
- Login page
- Vehicle dashboard
- Search and filters
- Vehicle cards or rows
- Purchase button
- Disabled Purchase button when stock is zero
- Admin forms for adding, editing, and deleting vehicles
- Responsive, visually polished design

“Single-page application” does not mean literally one screen. It means React changes views without traditional full-page reloads.

## What “purchase” means here

They are not asking you to build Stripe payments, checkout, invoices, or delivery.

The minimum meaning is:

1. User clicks Purchase.
2. Backend checks that stock is greater than zero.
3. Backend decreases quantity, normally by one.
4. Updated quantity appears in the UI.
5. If stock reaches zero, Purchase becomes disabled.

A particularly strong implementation handles two users trying to buy the final vehicle simultaneously. If stock is `1`, exactly one purchase should succeed; the other should receive an “out of stock” response. Stock must never become `-1`.

That small detail demonstrates real backend engineering much better than adding several flashy features.

## TDD is one of the biggest parts of the assessment

“TDD” means:

1. **Red:** Write a test for behaviour that does not exist yet. The test fails.
2. **Green:** Implement the smallest correct solution. The test passes.
3. **Refactor:** Improve the code while keeping the tests passing.

For example:

```text
test: reject purchase when inventory is zero (red)
feat: prevent purchases when inventory is empty (green)
refactor: move stock rules into inventory service
```

They explicitly want this pattern visible in your commit history, particularly for backend logic. Therefore, building the entire application first and adding tests afterward would miss a central requirement—even if coverage eventually says 95%.

Meaningful tests should cover things such as:

- Duplicate registration
- Incorrect password
- Missing or expired token
- Normal user attempting an admin action
- Invalid price or quantity
- Search by make, model, category, and price
- Purchasing the final unit
- Attempting to purchase at zero stock
- Restocking with an invalid amount
- Two concurrent purchases of the final unit

There is no exact required coverage percentage in the brief.

## Decisions the brief leaves to you

Several details are deliberately unspecified. A good candidate makes sensible decisions and documents them:

- Public registration creates only normal users.
- Admin is created through a seed command or bootstrap configuration.
- Create, update, delete, and restock are admin-only.
- Sold-out vehicles remain visible so their disabled button can be seen.
- One purchase decreases stock by one.
- Restock accepts a positive integer quantity.
- Search filters can be combined.
- Minimum and maximum prices are inclusive.
- Price is stored safely as a decimal or integer cents, not an imprecise floating-point value.
- Quantity can never be negative.
- General vehicle editing should not secretly bypass purchase/restock inventory rules.

Having documented assumptions is better than silently guessing.

The project pipeline you should understand for the interview is:
